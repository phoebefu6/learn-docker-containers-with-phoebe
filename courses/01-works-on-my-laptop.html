Why it works on your laptop and nowhere else

A project that runs on one machine is not a project that runs. It is a project plus a machine, and the machine is carrying half the instructions in places nobody reads: the Python it happens to have, a library installed by hand last spring, a password in a shell profile, a file at a path with someone's name in it. Tonight we find those instructions, sort them, and decide where each one should be written down instead.

Part 0

Where we start

One question runs through all six sessions: if your laptop died tonight, could a teammate run your project tomorrow with one command, and how long would the rebuild take? A container is the cheapest honest answer, because a container is a written-down environment: every assumption the laptop was making, turned into a line a machine can check. We carry one running case the whole way, the Constructed Stackyard example: a four-person analytics team with a Jupyter notebook, a small FastAPI scoring API, a nightly Python job and a Postgres database, all of which work on exactly one analyst's laptop. Each session adds one piece to Stackyard's container kit.

Part 1 · covers hidden dependencies

Seven things your project needs that nobody wrote down

6 min live

When the Stackyard scoring API starts, it reaches for far more than its own code. Some of what it reaches for is written down, in Git or in requirements.txt. Most of it is just there, on the laptop, because somebody put it there once. A hidden dependency is anything the program needs that the repository does not describe. The figure is the scoring API on the analyst's laptop, with every reach drawn.

LiveThe seven kinds, and how each one breaks a teammate's run4 min▶

Python version. The laptop has 3.12. A teammate's machine has whatever it has. Code that uses a 3.12 feature fails on 3.10 with a syntax error, and a pickled model or a joblib file saved under one version may refuse to load under another.

Packages. requirements.txt says pandas and scikit-learn with no versions, so "install the requirements" means "install whatever is newest today". The laptop has the versions from the day the analyst first ran pip install. Those two sets drift apart a little every week.

OS libraries. Some Python packages lean on system libraries that pip does not install. The analyst ran brew install libomp to fix an import error months ago and forgot. Nothing in the repository mentions it.

Environment variables. DB_PASSWORD is exported in the analyst's shell profile. On any other machine it is simply absent, and the API fails at its first database call, often with an error that never mentions the variable.

Files and services. The scoring code reads /Users/ana/data/scores_2025.parquet, a path with a person's name in it, and connects to Postgres on localhost:5432, a database that exists because Homebrew started it at login.

The clock. The nightly job runs from the analyst's crontab at 02:00 in the laptop's time zone. When the laptop sleeps, the job does not run. When the laptop flies to another time zone, "nightly" moves with it.

The code. In Git, reviewed, versioned. The one part that is fully written down, and the one part nobody was worried about.

Self-studyWhy a requirements file is not enough on its own3 min▶

A requirements file only describes one of the seven kinds, and even that one partially. Without versions it describes a moving target. With top-level versions only, every package those packages need (numpy under pandas, scipy and joblib under scikit-learn) still floats. And a pinned version is not a pinned file: the same version of numpy ships as different wheel files for different operating systems, processor types and C libraries, so "numpy 2.5.5" on a Mac and on a Linux server are two different binaries.

Pin every package, including the ones you did not ask for by name, which pip freeze on a working environment will print for you. Then accept that the file still says nothing about Python itself, the OS, the variables, the files, the services or the clock. That is the gap a container closes.

Real world

Even the base image moves. At the time of writing, the official python:latest image on Docker Hub is Python 3.15.2: its tag list reads "3.15.2, 3.15, 3, latest". A Dockerfile written today as FROM python:latest on a team that develops on 3.12 is already building on a different Python, and Docker's own best-practice guide says why: "Image tags are mutable, meaning a publisher can update a tag to point to a new image." Writing the environment down only helps if what you write down stays put. Session 2 shows how to pin it.

Part 2 · covers virtualenv, container and virtual machine

What a virtualenv, a container and a VM each write down

5 min live

There are three common tools for "make it run somewhere else", and the useful way to compare them is not speed or fashion but coverage: which of the layers under your code does each one carry with it, and which does it borrow from whatever machine it lands on? Hatched bars below travel with the project. White bars are not carried: they come from whatever machine the project lands on, or, for the code, from Git beside it.

LivePick the tool by what differs between the machines3 min▶

If the only thing that differs is package versions, and everyone already has the same Python on the same OS, a virtualenv plus a fully pinned requirements file is enough, and it is the lightest tool in the room. Most data teams are not in that situation: one analyst on a Mac, one on Windows, a server on Linux, and three Pythons between them.

A container carries the OS libraries and the interpreter as well, so the Mac, the Windows laptop and the Linux server all run the same Debian, the same Python 3.12 and the same packages. It borrows only the kernel, which is why it starts in about the time a process takes to start, rather than the time a machine takes to boot.

A virtual machine carries its own kernel too. You reach for one when the kernel itself matters: a different operating system altogether, or isolation strong enough to run code you do not trust. For "the notebook only runs on Ana's laptop", it is more machine than the problem needs.

Self-studyGetting Docker onto a machine, and what the licence says3 min▶

Nothing in these six sessions needs Docker installed: every build-along runs in the page. When you do install it, there are several routes. Docker Desktop is the most common on Mac and Windows. Read its licence before you install it at work: at the time of writing, Docker's terms restrict free use to non-commercial open source projects and to commercial organisations with "fewer than 250 employees and less than US $10,000,000" in annual revenue; larger organisations and government entities need a paid subscription. Docker Engine and the other open source Moby components are not covered by that restriction.

Alternatives that run the same images include Podman, Colima and Rancher Desktop. Which one your company allows is a question for whoever owns your laptops, not for a tutorial; ask before you install.

Real world

Where the kernel comes from on a laptop. Containers share a Linux kernel, and macOS and Windows do not have one. Docker's own documentation is direct about the workaround: "Docker Desktop supports multiple Virtual Machine Managers (VMMs) to power the Linux VM that runs containers." On a Mac, then, your containers share the kernel of one small Linux VM that Docker Desktop manages, and on a Linux server they share the server's own. The image is the same in both places; that is the point.

Part 3 · covers the container kit

The container kit, one piece a session

4 min live

Stackyard does not need a platform. It needs four things written down well enough that a teammate can type one command: what the image is built from, how the API image is built, how the pieces run together, and what has to be true before an image ships. Over six sessions we build exactly that, and measure the rebuild time on the way.

LiveTwo numbers to carry: one command, and the rebuild3 min▶

One command. The test of the kit is not "is there a Dockerfile". It is whether a teammate with Docker and the repository, and nothing else, can start the notebook, the API and the database by typing docker compose up. Every hidden dependency on tonight's list either gets written into one of the kit's files or gets written into the short README that says what the command needs (a filled-in .env, for example). Nothing stays in anyone's head.

The rebuild. A container that takes a minute to rebuild after a one-line code change gets bypassed: people go back to running things on their laptops "just for now". So the kit is also measured. On the session 4 bench, Stackyard's first naive Dockerfile takes a modelled 52.1 seconds to rebuild after a one-line change to the scoring code; the same Dockerfile with its lines in a better order takes 0.5 seconds. Same files, same packages. Session 4 shows exactly why.

Self-studyWhat the kit deliberately leaves out2 min▶

No orchestrator, no cloud, no registry pipeline. Running containers on a cluster or a cloud service is a real next step and session 6 ends with a card pointing at it, but Stackyard's problem is not scale; it is that the project only exists on one machine. Docker as one piece of a full CI and deployment platform is taught in DataOps, builder session 1; here we teach Docker itself, properly, so that piece makes sense when you get there.

Real world

Why the order of lines matters before you have written one. Docker's documentation on the build cache states the rule the whole of session 4 is built on: "Once a layer changes, then all downstream layers need to be rebuilt as well." A Dockerfile is not a list of settings. It is a sequence, and where you put the line that changes most often decides how much of the sequence runs again.

Build-along

Stackyard's dependency inventory

★ 22 min · everyone builds

Below is the evidence from the analyst's laptop (Constructed Stackyard example): a few lines of shell history, the shell profile, the crontab, the requirements file and one line of the scoring code. You will find every hidden dependency in it, sort each into one of the seven kinds, and write down where in the container kit it will live from now on. Nothing to install: the evidence and the worksheet are the whole kit for tonight.

Read the evidence as a stranger. You are the teammate who has to run Stackyard tomorrow on a fresh machine. Read the evidence below once, slowly, and mark every line that assumes something about the machine rather than the project.

★ Step 1 · evidence from the analyst's laptop (constructed)$ tail ~/.zsh_history brew install python@3.12 brew install postgresql@16 && brew services start postgresql@16 brew install libomp # fixed "Library not loaded: libomp.dylib" pip install pandas scikit-learn fastapi uvicorn psycopg2-binary $ grep -i stackyard ~/.zshrc export DB_PASSWORD=stackyard-dev-123 export STACKYARD_DATA=/Users/ana/data $ crontab -l 0 2 * * * cd ~/stackyard && python jobs/nightly_scores.py $ cat requirements.txt pandas scikit-learn fastapi uvicorn $ grep -n parquet app/scoring.py 14: SCORES = pd.read_parquet("/Users/ana/data/scores_2025.parquet")

Sort every finding into one of the seven kinds. Python version, packages, OS libraries, environment variables, files and services, the clock, the code. One finding can expose two kinds; write both. Then compare with one reading below.

★ Step 2 · one reading of the inventoryPython version 3.12, from Homebrew; nowhere in the repository Packages 4 names in requirements.txt, no versions; psycopg2-binary installed by hand, missing from the file OS libraries libomp, installed by hand to fix an import error Env variables DB_PASSWORD (a secret) and STACKYARD_DATA, in ~/.zshrc Files /Users/ana/data/scores_2025.parquet, hard-coded in scoring.py line 14, ignoring STACKYARD_DATA anyway Services Postgres 16, started by brew services at login The clock nightly job at 02:00 in the laptop's time zone, and only when the laptop is awake The code in Git: app/, jobs/, notebooks/

Give each one a home in the kit. For every line of the inventory, write which file will carry it from now on and which session builds that file. Use the figure above as the answer key only after you have tried. Notice the one that must never go into the image at all.

★ Step 3 · the inventory with a home columnPython 3.12 -> FROM python:3.12-slim in the Dockerfile (s3) packages -> requirements.txt, every package pinned (s3) psycopg2-binary -> added to requirements.txt, pinned (s3) libomp -> a written install line, or a recorded check that the Linux wheel does not need it (s3) DB_PASSWORD -> .env read by Compose, kept out of the image and out of Git (s5, s6) STACKYARD_DATA -> environment: in compose.yaml (s5) the parquet file -> a volume mounted at /data; scoring.py reads the path from STACKYARD_DATA (s5) Postgres 16 -> a db service in compose.yaml, image pinned (s5) 02:00 nightly -> TZ set explicitly; the job as a one-off service run on a schedule (s5)

Fix the one line of code the kit cannot fix for you. A container can mount the data anywhere you like, but it cannot make a hard-coded /Users/ana path exist. Change line 14 so the path comes from the environment, with no default that points at a person.

★ Step 4 · scoring.py line 14, before and after# before: works on one laptop SCORES = pd.read_parquet("/Users/ana/data/scores_2025.parquet") # after: the environment says where the data is import os DATA_DIR = os.environ["STACKYARD_DATA"] # fails loudly if unset SCORES = pd.read_parquet(os.path.join(DATA_DIR, "scores_2025.parquet"))

Score the inventory, then save it. Grade it on the six rows below. Save the result as docs/dependency-inventory.md in the repository: that file is piece one of Stackyard's container kit, and session 6 scores the whole kit with the same honesty.

The Python version is written down, to the minor version "Python 3" scores 0. "3.12" scores the point.
Every package is listed, including the ones installed by hand Here, psycopg2-binary was installed but never added to the file.
Every system library or tool installed outside pip is listed Or there is a written note that it is not needed in the container, and how you checked.
Every environment variable is named, and secrets are marked as secrets Names in the inventory; values never. A secret value in a shared document is a leak.
No path in the code contains a person's name or home folder Data locations come from configuration, with no personal default.
Every service and every schedule has an owner other than one laptop Postgres and the nightly job each have a line saying where they will run.

Run it on a fresh machine, not in your head. The cheapest honest test of an inventory is a colleague with a clean laptop (or a fresh cloud shell) following only what is written. Every place they have to ask you a question is a line missing from the inventory.

Homework

Before session 2

30 min
  1. Run the inventory on a project of your own. One you could not hand to a colleague today. Use the seven kinds from Part 1 as columns and fill every one, even if the answer is "none".
  2. Find the hand-installed thing. Search your shell history for brew install, apt install, conda install or a manual download. Which of those does your project silently need?
  3. Grep for personal paths. Search the repository for your username and for /Users/, /home/ and C:\Users. Every hit is a file the container cannot find.
  4. Pin what you have. In your working environment, run pip freeze and compare it with your requirements file. Count the packages that are installed but not listed; bring the number to session 2.
Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · Stackyard's requirements file lists pandas and scikit-learn with no versions. A teammate installs it today and the model file will not load. What is the most precise description of the problem?

An unpinned name describes a moving target. Pin every package, including the ones underneath the ones you asked for, and the version on the laptop and the version in the container stop drifting apart.

2 · What does a container carry with the project that a virtualenv does not?

A virtualenv carries packages and borrows everything under them. A container carries everything above the kernel, which is the part that differs between laptops. A virtual machine is the one with its own kernel.

3 · DB_PASSWORD lives in the analyst's shell profile. Where does Stackyard's container kit put it?

A secret is a dependency whose value must not be written down where everyone can read it. Anything baked into an image travels with the image to everyone who can pull it; session 6 shows exactly how, and how to keep it out.
