Images, containers, layers: the mental model

Most Docker confusion comes from one blurred line: the image and the container are not the same thing. An image is a stack of read-only filesystem changes with a name on top. A container is that stack plus one thin writable layer and a running process. Once the line is sharp, three everyday surprises stop being surprises: where your files went, why the image did not shrink, and why the same tag built something different last week.

Part 1 · covers image vs container and the writable layer

One image, many containers, one writable layer each

6 min live

An image never runs. It is a template, read-only, sitting on disk or in a registry. When you start a container from it, Docker does not copy the image; it puts a small, empty, writable layer on top of the image's layers and starts a process that sees all of them as one filesystem. Start three containers and you get three writable layers over one shared image. The figure is the Stackyard API image as rung 6 of the session 4 ladder builds it (Constructed Stackyard example), running three times.

LiveImage, container, writable layer4 min▶

The image is the template. Docker's own definition is one line: an image is "a read-only template with instructions for creating a Docker container." Read-only is the important word. Nothing you do inside a running container changes the image it came from.

The container is the running instance. "A container is a runnable instance of an image." When it starts, Docker creates a directory just for that container on top of the image's layers. That directory is the writable layer: every file the process creates, changes or deletes is recorded there, and the image layers underneath stay exactly as they were.

Many containers, one image. Run the Stackyard API three times to handle more requests and you have three writable layers over one copy of the image. That is why starting a second container is fast and cheap: almost nothing is copied.

Removing a container removes its writable layer. If container api-2 wrote /tmp/scores.csv and you remove api-2, the file is gone. For a scratch file that is fine. For Stackyard's Postgres database it would be a disaster: every row lives in the database container's writable layer unless you put the data somewhere that outlives the container. That somewhere is a volume, and session 5 mounts one.

Self-studyWhat docker run actually does3 min▶

docker run is three steps in one command. First, if the image is not already on the machine, Docker pulls it from a registry (Docker Hub, unless the name says otherwise). Second, it creates a container: the writable layer on top of the image's layers, plus the configuration the image carries, such as the start command and environment variables. Third, it starts the process.

If you have Docker, you can watch the line between image and container. Your output will differ from anything printed here, so read it rather than compare it.

★ If you have Docker · three containers, one imagedocker run -d --name demo-1 python:3.12-slim sleep 600 docker run -d --name demo-2 python:3.12-slim sleep 600 docker exec demo-2 sh -c 'echo hello > /tmp/note.txt' docker exec demo-1 ls /tmp # empty: demo-1 has its own writable layer docker ps # two containers, one image name docker rm -f demo-2 # its writable layer, and note.txt, are gone docker image ls python # the image is still there
Real world

Docker's own three definitions. The Docker overview defines the vocabulary in three short sentences worth memorising as a set: "An image is a read-only template with instructions for creating a Docker container." "A container is a runnable instance of an image." "A Docker registry stores Docker images." Every confusing moment in the first month with Docker is one of those three words used in place of another.

Part 2 · covers layers as filesystem diffs

A layer is a diff, and diffs only add

5 min live

Docker's description of a layer is precise: "Each layer in an image contains a set of filesystem changes - additions, deletions, or modifications." A union filesystem stacks those changes so the container sees one merged tree. Read that model carefully and one consequence falls out that catches almost everyone: a layer can say "this file is deleted", but it cannot reach down and remove the bytes from the layer that added them. The figure is the Constructed Stackyard example at rung 4 of the session 4 ladder, layer by layer.

LiveWhich instructions make layers3 min▶

Lines that change files make layers that hold bytes. RUN runs a command and records every file it added, changed or deleted. COPY brings files in from the build context. ADD does the same and can also fetch remote URLs and unpack local archives, which is why plain COPY is the default choice for local files.

Lines that change settings carry configuration. ENV, EXPOSE, CMD, USER and LABEL change how a container from the image starts: its variables, its documented port, its start command, its user, its metadata. They add no files. Docker's best-practice guide does say that "Each ENV line creates a new intermediate layer", and that is Docker's wording for how the build records each step; in the lab they appear as configuration with 0 MB, because no file bytes are added.

WORKDIR sits in between. It sets the working directory and creates it if it is missing. The session 4 lab counts it as a build step and prints 0 MB for it.

The practical read. When you look for weight in a Dockerfile, look only at RUN, COPY, ADD and the FROM line. Everything else is cheap to move, and session 4 moves several of them on purpose.

Self-studyUnion filesystem and sharing3 min▶

A union filesystem presents several directories stacked on top of each other as one directory. When the container reads /usr/local/lib/python3.12, it sees the topmost version of every file across all the layers. When a later layer deletes a file, the union view hides it, but the earlier layer still contains it. That is the whole reason the apt lists and the pip cache in rung 4 stay in the image: they were added in a layer, and nothing later can subtract from that layer. Docker's best-practice guide therefore says to combine apt-get update and apt-get install in one RUN and to remove /var/lib/apt/lists to reduce size, all in that same line; the clean-up only saves bytes if it happens before the layer is sealed.

The same stacking is what makes layers cheap to share. Layers are stored by content, so two different images built on python:3.12-slim store the slim base once on your disk and in a registry, and a pull downloads only the layers you do not already have. A team that standardises on one base image pays for it once per machine.

If you have Docker, docker history python:3.12-slim lists an image's build steps with their sizes; your output will differ, because the tag moves.

Real world

Every official image is built on someone else's layers. Docker's page on image layers puts the payoff in one line: "Layers let you extend images of others by reusing their base layers". The python:3.12-slim image is itself Debian plus a Python build, and at the time of writing it is 3.12.16-slim-trixie, Debian 13 underneath. Stackyard's image will be the slim image plus four or five layers of its own; nobody on the team has to build Debian or Python.

Part 3 · covers tags, digests, registries and OCI

A tag is a pointer, a digest is the content

4 min live

When Stackyard's Dockerfile says FROM python:3.12-slim, that name is not the image. It is a tag: a label in a registry that points at an image, and that the publisher can point somewhere else tomorrow. Underneath the tag is a digest, a hash of the content, which can never point anywhere else. The figure follows the real python:3.12-slim tag on Docker Hub at the time of writing, read 2026-11-16, down to the layers a Constructed Stackyard example build would pull.

LivePin by tag or by digest3 min▶

Floating tag. FROM python:latest means "whatever the publisher calls latest today". At the time of writing that is Python 3.15.2, not the 3.12 Stackyard's laptop runs. Never ship on it.

Pinned tag. FROM python:3.12-slim fixes the Python minor version and the variant. It still moves: Docker's guide says plainly that "Image tags are mutable, meaning a publisher can update a tag to point to a new image." Each move usually brings patch releases and security fixes, which is mostly what you want, but it means two builds a week apart can start from different bytes.

Digest pin. FROM python:3.12-slim@sha256:5e2bdb1b... (the full 64-character hash in a real file) names the content itself. Pinning to a digest fully fixes the version, so every build starts from the same base until a person changes the line. The price is that security fixes arrive only when someone updates the digest on purpose; session 6 puts that decision on the release checklist.

Pin the index, not a platform manifest. The digest worth pinning is the image index, because it still resolves to the right manifest on an Apple silicon laptop (arm64) and on a Linux server (amd64). A manifest digest names one platform's image only, so pinning the amd64 manifest hands an arm64 laptop the amd64 image.

Self-studyWhat is inside an OCI image3 min▶

Docker images follow the Open Container Initiative image format, which is why Podman, containerd and every major registry read the same images. The spec names four parts: an image manifest, an optional image index, a set of filesystem layers, and a configuration. Each layer is referenced by a content-addressable identity, a digest of its bytes, so two images that share a layer share it by hash, not by name.

The index lists one manifest per platform. The manifest lists the layers for that platform, in order, plus the configuration. The configuration carries what Part 2 called config lines: environment variables, the start command, the user, the exposed ports. The layers are the filesystem diffs. The real python:3.12-slim tag at the time of writing shows the whole chain: one index digest, an amd64 manifest of 43.27 MB and an arm64 manifest of 43.54 MB, compressed.

Registries. A registry stores images by these digests and keeps the tag pointers. Docker looks on Docker Hub by default, so python:3.12-slim means Docker Hub's official python image unless the name starts with another registry's host. Pushing Stackyard's own images to a registry from CI is taught in GitLab, builder session 7.

If you have Docker, docker buildx imagetools inspect python:3.12-slim prints the index and its per-platform manifests; your digests will differ, because the tag has moved since this was written.

Real world

The spec that makes images portable. The OCI Image Format specification defines an image as "an image manifest, an image index (optional), a set of filesystem layers, and a configuration". That one sentence is why the image Docker Desktop builds on a Mac runs unchanged under Podman on a Linux server: both tools read the same four parts, and both find layers by the same content hashes.

Build-along

Read a Dockerfile, predict its layers

★ 22 min · everyone builds

Below is the Dockerfile someone on the Stackyard team wrote for the scoring API (Constructed Stackyard example). It is rung 4 of the session 4 ladder: already ordered so the dependencies install before the code is copied, already on a pinned slim base, and still carrying some weight it does not need. Nothing gets built tonight. You will read it the way a reviewer does: line by line, predicting what each line produces, then check your predictions against the numbers the session 4 lab prints for exactly this file.

Mark every line: layer or configuration. Read the Dockerfile and write layer next to every line that changes files and config next to every line that only changes how the container starts. Use Part 2's rule: RUN, COPY and ADD change files; ENV, EXPOSE, CMD, USER and LABEL change configuration. Compare with one reading below.

★ Step 1 · the rung 4 Dockerfile, marked (constructed)FROM python:3.12-slim # base layers (pulled) WORKDIR /app # step, 0 MB RUN apt-get update && apt-get install -y curl # layer COPY requirements.txt . # layer RUN pip install -r requirements.txt # layer COPY . . # layer ENV DB_PASSWORD=stackyard-dev-123 # config EXPOSE 8000 # config CMD uvicorn app.main:app --host 0.0.0.0 --port 8000 # config

Predict the biggest layer, and say why. Before you look, pick the line you think adds the most bytes and write one sentence of reasoning. The trap is to say "the base image": it is big, but it is not the biggest.

★ Step 2 · one predictionBiggest: RUN pip install -r requirements.txt Why: it installs fourteen pinned packages, numpy, pandas, scipy and scikit-learn among them, and because the line has no --no-cache-dir, pip also keeps its download cache inside the same layer. The packages are counted twice: once installed, once cached. Runner-up: the base image, then the apt line, which keeps the apt lists because nothing removes them inside the same RUN.

Predict what rebuilds after a one-line change to app/scoring.py. Find the first line whose input includes that file. That line and every line below it run again; everything above it comes from the cache. This is a preview of session 4, which measures it.

★ Step 3 · one predictionCached: FROM, WORKDIR, RUN apt-get, COPY requirements.txt, RUN pip install (none of their inputs include app/scoring.py) Rebuilt: COPY . . (its input is the whole project, scoring.py included) ENV, EXPOSE, CMD (below the changed line; configuration, near-instant) Why the order is good: the heavy pip layer sits ABOVE the line that copies the code, so a code change never reinstalls the packages.

Check your read against the lab. These are the rung 4 rows the session 4 lab prints for exactly this Dockerfile. The base and package sizes are real, read from Docker Hub and PyPI on 2026-11-16; the apt and pip-cache sizes and all the times are modelled. Score yourself one point for each prediction that matched.

Keep the predictions you got wrong: they are the most useful lines in the file for the next person who reads a Dockerfile. Note the three things a reviewer would flag; session 4 fixes the weight and session 6 fixes the rest.

Every line is marked layer or configuration RUN, COPY and ADD hold files; ENV, EXPOSE, CMD hold settings.
The biggest layer is named, with the reason The pip install, because the cache is kept alongside the packages.
The rebuild after a code change is predicted from the first line that reads the code COPY . . and everything below it; nothing above.
Bytes a later line cannot remove are spotted The apt lists and the pip cache stay in the layers that wrote them.
The secret in the ENV line is flagged Anything in the image, config included, travels to everyone who pulls it.
The base is identified as a tag, not a fixed version And the read says when a digest pin will be decided.

Read the FROM line twice. It is the one line whose content you did not write and cannot see in the repository. Ask two questions of it every time: which Python and which OS does this tag mean today, and what will it mean the next time someone builds?

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Stackyard's API container writes /tmp/scores.csv. Someone removes the container with docker rm and starts a new one from the same image. Where is the file?

The image is read-only and each container gets its own writable layer. Remove the container and its writable layer goes with it. Data that must survive, like Stackyard's Postgres rows, belongs in a volume; session 5 mounts one.

2 · A Dockerfile runs RUN apt-get update && apt-get install -y curl, then on the next line RUN rm -rf /var/lib/apt/lists/*. Why does the image not get smaller?

Layers only add. The union view hides the deleted files, but the layer that added them is unchanged and is pulled with the image. Docker's best-practice guide combines update, install and the lists clean-up in one RUN so the bytes never get sealed into a layer.

3 · What does FROM python:3.12-slim@sha256:... protect against that FROM python:3.12-slim does not?

Both lines already fix the Python minor version and the slim variant. Only the digest fixes the content: tags are mutable, a digest is a hash of exactly one image index. The trade is that security fixes arrive only when you update the digest yourself.
