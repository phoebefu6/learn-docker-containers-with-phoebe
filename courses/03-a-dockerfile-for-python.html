Part 1 · covers FROM, WORKDIR, COPY, RUN, ENV, EXPOSE

Six instructions, and the moment each one acts

6 min live

Every instruction in a Dockerfile does its work at one of two moments. Some change files while the image is being built, and those files become a layer that travels with the image. Others only write a setting into the image's configuration, which does nothing until somebody starts a container from it. Mixing the two up is the source of most Dockerfile surprises. The figure sorts the instructions Stackyard's API needs (Constructed Stackyard example) into those two lanes.

LiveSix instructions and the job of each4 min▶

FROM picks the image you build on top of: every layer of the base sits under yours. For Stackyard it is python:3.12-slim, because session 1's inventory found Python 3.12 on the laptop. Part 3 explains why the tag is spelled out in full.

WORKDIR sets the folder that every later RUN, COPY and CMD works in, and it is the folder the container starts in. Docker's best-practice guide says to always use absolute paths, and hadolint, the widely used Dockerfile linter, has a rule for it: DL3000, "Use absolute WORKDIR." WORKDIR /app, never WORKDIR app, so nobody has to guess where "here" is.

COPY copies files from the build context (the folder you send to the builder) into the image, as a new layer. Its cousin ADD can also fetch remote HTTPS and Git URLs and unpack local archives. For ordinary local files use COPY: hadolint's DL3020 reads "Use COPY instead of ADD for files and folders." Reach for ADD only when you actually want the fetch or the unpack.

RUN executes a command inside the image as it stands so far, and whatever the command writes to disk becomes the next layer. pip install lives here, and so does creating a user.

ENV sets an environment variable that is baked into the image's configuration and present in every container started from it. Anyone who can pull the image can read it, which is why hadolint's DL3064 says "Potentially sensitive data should not be used in the ARG or ENV commands". A password in ENV is a password in the image. Session 6 shows how secrets reach a build safely; session 5 shows how they reach a running container.

EXPOSE is the one people misread most. In Docker's own words it "doesn't actually publish the port". It documents which port the app listens on. Publishing it to your laptop is a run-time decision: docker run -p 8000:8000.

Self-studyARG vs ENV3 min▶

ARG declares a build-time input: a value you pass with docker build --build-arg NAME=value so one Dockerfile can build, say, two Python versions. ENV sets a variable in the image's configuration, so it is still there when a container runs. The everyday rule of thumb: ARG to steer the build, ENV for settings the running app needs and that are safe to publish, such as a log level.

What neither of them is for: secrets. Docker's "Build secrets" page is blunt that build arguments and environment variables "are inappropriate for passing secrets to your build" because "they persist in the final image". The right tool is a secret mount that exists only for one RUN line, which session 6 teaches. Until then, the safe habit is the one hadolint's DL3064 encodes: no name containing PASSWORD, SECRET, TOKEN or KEY anywhere near an ARG or ENV line.

Real world

The port that was never published. The Dockerfile reference says EXPOSE "doesn't actually publish the port"; it is documentation between the person who wrote the image and the person who runs it. Publishing happens with -p or -P on docker run, or with ports: in Compose, which is session 5. So when a teammate writes "I added EXPOSE 8000 and still cannot reach the API", the Dockerfile is fine. The missing piece is on the command line.

Part 2 · covers CMD vs ENTRYPOINT, exec vs shell form

What actually starts when you type docker run

5 min live

An image carries a default command, and the person running it can override some or all of that default from the command line. Two instructions decide which part is overridable: CMD and ENTRYPOINT. Stackyard (Constructed Stackyard example) needs both behaviours. The API is a service that should start uvicorn by default, while still letting you poke inside. The nightly job is a tool: the image should always run the job, and you only add arguments.

LiveCMD for a service, ENTRYPOINT for a tool3 min▶

CMD is the image's default command, and the Dockerfile reference is precise about it: "There can only be one CMD instruction in a Dockerfile. If you list more than one CMD, only the last one takes effect." Anything you type after the image name on docker run replaces it. For the API that is exactly right: docker run stackyard-api starts the service, and docker run stackyard-api python -c "print(1)" lets you check that Python and the packages work without starting uvicorn at all.

ENTRYPOINT "allows you to configure a container that will run as an executable". Whatever you type after the image name is added to it as arguments instead of replacing it. For the nightly job, that is the behaviour you want: the image is the job, and the only thing a scheduler should vary is the arguments. Docker's best-practice guide puts the pairing in one line: use ENTRYPOINT for the image's main command, and CMD for default flags.

The test that decides which you need: would anyone ever want to run something other than the main program in this image? For a service, yes (a shell check, a migration, a one-off script), so use CMD. For a single-purpose tool, no, so use ENTRYPOINT.

Self-studyShell form and exec form side by side3 min▶

CMD and ENTRYPOINT each come in two spellings. Shell form is a plain string, the way you would type it at a prompt. Exec form is a JSON array, one element per word:

# shell form: one string, split up by a shell
CMD uvicorn app.main:app --host 0.0.0.0 --port 8000

# exec form: the program and each argument, already separated
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Docker's best-practice guide recommends the exec form, ["executable", "param1"], because it avoids shell string munging: nothing reinterprets your quotes, spaces or special characters on the way to the program. hadolint asks for the same thing with DL3025, "Use arguments JSON notation for CMD and ENTRYPOINT arguments". Every preset Dockerfile in the session 4 lab that still uses the shell-form CMD trips that rule; the hardened one does not.

One practical trap in exec form: it must be valid JSON, so the quotes are double quotes. CMD ['uvicorn', 'app.main:app'] with single quotes is not a JSON array.

Real world

The second CMD that quietly wins. Dockerfiles grow by copy and paste, and it is easy to end up with a CMD near the top from an old template and another at the bottom. The Dockerfile reference settles it: "only the last one takes effect". Nothing warns you at build time. If a container starts the wrong program, read the file from the bottom up and find the last CMD first.

Part 3 · covers .dockerignore, pinning and a non-root USER

Decide what the builder sees, what it installs, and who it runs as

4 min live

Three habits separate a Dockerfile that works today from one that still works, and still is safe, next quarter. Keep the build context to what the image needs. Pin the base image and every package to an exact version. And stop the app from running as root. On the Constructed Stackyard example, the first habit alone changes what reaches the builder from 604.32 MB in 16 files to 4.31 MB in 7 files, as the session 4 lab prints for rungs 1 and 2, and it keeps the password file off the builder entirely.

LivePin the base, pin every package2 min▶

The base. Write FROM python:3.12-slim, never FROM python or FROM python:latest. At the time of writing, latest is Python 3.15.2, not the 3.12 that Stackyard was written and tested on, and it is the full image: 419.02 MB compressed, as Docker Hub lists it, against 43.27 MB for python:3.12-slim. hadolint has two rules for this: DL3006 "Always tag the version of an image explicitly." and DL3007 "Using latest is prone to errors if the image will ever update. Pin the version explicitly to a release tag." A tag can still be re-pointed by its publisher; pinning to a digest fixes it completely, which session 2 showed and session 4 measures.

The packages. Every package, including the ones you never asked for by name, with == and an exact version. Stackyard's API needs fourteen, and the build-along pins all of them to the releases on PyPI at the time of writing: fastapi, starlette, pydantic, pydantic-core and uvicorn for the API; pandas, numpy, python-dateutil and tzdata for the data; scikit-learn, scipy, joblib and threadpoolctl for the model; psycopg2-binary for Postgres, the one session 1 found installed by hand and missing from the file.

Self-studyWhy non-root, and what hadolint does and does not check3 min▶

Unless a Dockerfile says otherwise, the app in the container runs as root. Docker's best-practice guide gives the rule in one sentence: "If a service can run without privileges, use USER to change to a non-root user." A scoring API needs no privileges: it reads its own code and model and listens on port 8000. So Stackyard creates an ordinary account with useradd and switches to it with USER before the CMD. If something ever goes wrong inside the process, it goes wrong with an ordinary user's permissions.

Here is the part people miss. hadolint's DL3002 reads "Last user should not be root", and it fires only when the last USER line in the file names root. A Dockerfile with no USER line at all, which is most of them, does not trip it, even though the container then runs as root by default. A clean hadolint run is therefore not proof of a non-root image. The session 4 lab closes that gap with a rule of its own, DKR-USER, which fires when the final stage never sets USER, and it labels the rule as the lab's, not hadolint's.

If you have Docker, check any image you already use: docker image inspect --format '{{.Config.User}}' IMAGE. An empty answer means root.

Real world

What "slim" leaves out. The official python image's documentation describes the slim variant as containing "only the minimal Debian packages needed to run python". What is missing is the toolchain for compiling extension modules. That is fine as long as pip finds a ready-built wheel for every package, and at the time of writing all fourteen of Stackyard's packages publish a ready-built wheel on PyPI that installs on slim (a cp312 manylinux wheel, or a pure-Python one). Add a package that has no wheel for your platform, though, and the install fails on slim where it worked on the full image. The fix is a deliberate one (install the build tools, or build in a separate stage, which is session 6), not a quiet switch back to latest.

★ Step 2 · .dockerignore# keep the build context to what the image needs .git .venv .env data/ notebooks/ tests/ **/__pycache__ *.pyc Dockerfile .dockerignore

Write the Dockerfile, one line and one comment at a time. Type each instruction only after you can say what it writes and when. Put each comment on its own line: Docker treats # as a comment only at the start of a line, so a comment tacked onto the end of an instruction becomes part of its arguments. Order matters: the dependency list is copied and installed before the code, so a change to app/scoring.py leaves the install alone. Session 4 measures how much that saves.

★ Step 3 · Dockerfile, single stage, commented# Python version (session 1): 3.12 on slim Debian, pinned, never latest FROM python:3.12-slim # One absolute folder for everything below (DL3000) WORKDIR /app # The dependency list alone, before any code, so code edits do not reinstall COPY requirements.txt . # The 14 pinned packages; --no-cache-dir keeps pip's cache out of the layer (DL3042) RUN pip install --no-cache-dir -r requirements.txt # Only the API's code and model; .dockerignore keeps the rest on the laptop COPY app/ ./app/ # An ordinary account with a fixed uid RUN useradd --create-home --uid 10001 stackyard # From here on, including the running API, nothing runs as root USER stackyard # Documents the port the API listens on; docker run -p publishes it EXPOSE 8000 # The start command in exec form (DL3025); docker run arguments replace it CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Review it the way a reviewer would. The session 4 lab implements thirteen lint rules: ten modelled on hadolint rule ids and three of its own. Go through them by reading and predict, rule by rule, whether each one fires on your file. The six most likely to catch a first Dockerfile are DL3006, DL3007, DL3042, DL3025, DL3064 and DKR-USER; check those first. Then paste the file into the session 4 lab to check your prediction; its number is the one that counts. Read your Dockerfile from the container's side. For every line, ask two questions out loud: "does this change files or only settings?" and "if I deleted this line, what would a teammate have to know that is not written anywhere?" A line with no answer to the second question can probably go; a dependency with no line is a hidden one still.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · Stackyard's Dockerfile says EXPOSE 8000. A teammate runs docker run stackyard-api with no other flags and cannot reach the API from their browser at localhost:8000. What is going on?

The Dockerfile reference says EXPOSE "doesn't actually publish the port". It is a note from the image's author to whoever runs it. The -p flag (or ports: in Compose, session 5) is what connects a host port to the container.

2 · Image A ends with CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]. Image B is identical except that the same array is written as ENTRYPOINT instead. You run each one as docker run IMAGE python -c "print(1)". What starts?

Arguments after the image name replace CMD and are appended to ENTRYPOINT. That is why a service like the API uses CMD (you can still run a check inside it), and a single-purpose tool like the nightly job uses ENTRYPOINT (you only ever pass it arguments).

3 · A .dockerignore contains only *.pyc. Why does app/__pycache__/scoring.cpython-312.pyc still reach the builder?

Docker's build context documentation spells out that patterns are matched with Go's filepath.Match from the root of the context. ** matches any number of directories, which is why Stackyard's ignore file carries **/__pycache__ as well as *.pyc. The session 4 lab's unit tests encode exactly this case.
