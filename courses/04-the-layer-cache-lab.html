Stackyard's API has a Dockerfile now. The team's first one, written before session 3, still sits in a few branches, and it takes the better part of a minute to rebuild after a one-line change, which is how people quietly go back to running the API on their laptops. Part 1 · covers how the build cache decides

The cache rules, as the lab applies them

6 min live

Docker builds an image one instruction at a time and, before running each one, looks for a cached layer from an earlier build that matches it exactly. The rules for "matches" are short, and almost every slow build traces back to one of them. The figure is the same one-line change to app/scoring.py meeting two orderings of the same Dockerfile.

LiveFour rules, read at Docker's documentation4 min▶

1. Each instruction is matched against the cache in order. "If no cached layer matches the instruction exactly, the cache is invalidated."

2. COPY and ADD look at the files. For these, the builder computes a checksum from the copied files' metadata and contents, and "the cache is invalidated if the file metadata has changed for any of the files involved". The modification time alone does not count: touching a file without changing it leaves the cache intact.

3. RUN does not look at anything outside its own text. "The cache for RUN instructions isn't invalidated automatically between builds." A cached RUN pip install -r requirements.txt does not notice that PyPI has a newer pandas. It reruns only when something above it was invalidated.

4. Invalidation flows downhill. "Once a layer changes, then all downstream layers need to be rebuilt as well", even if they would build exactly the same thing. That is the rule the figure shows, and the reason line order is a performance decision.

The lab applies these four rules, plus one more from the multi-stage documentation: "BuildKit only builds the stages that the target stage depends on." A stage nobody copies from is skipped.

Self-studyWhat the lab computes, what it models, and what it leaves out3 min▶

Computed for real: the parse of the Dockerfile (instructions, line continuations, stages, COPY --from), the build context after .dockerignore (Go-style globs, **, ! exceptions, last match wins, as Docker documents them), which files each COPY picks up, the cache walk for the changed file, the layer list, and thirteen lint rules, each with a unit test that fires it and one that passes.

Real, read at source: the base image sizes (Docker Hub, linux/amd64, compressed, read 2026-11-16) and the Python package sizes (PyPI wheel files for Python 3.12 on x86_64, read the same day). Image size is the compressed base plus the layer sizes, so treat it as approximate.

Modelled, printed under the widget: every time in seconds, every apt and apk package size, and the Stackyard project files. A rebuild re-sends only the changed file, as BuildKit's incremental context transfer does. Your own builds will differ; the ordering of the rungs is the claim, not the decimals.

Left out: remote builders, cache exported to a registry, ARG values changing between builds, a changed instruction text (the lab changes files, not the Dockerfile), and anything about the network.

Real world

Docker's own advice, in Docker's own order. The documentation page "Optimize cache usage in builds" gives the fix as three steps: first copy the package management files, then install the dependencies, and finally copy the project source code, "which is subject to frequent change". The page's example is a Node project; for Python the package management file is requirements.txt, and the rule is identical.

Build-along · the bench

Six rungs, computed in front of you

★ 22 min · everyone builds

Each preset button is one rung of the ladder: the same Stackyard API, the same requirements, one improvement at a time. Pick a rung, pick the file that changed, and press Rebuild. The headline is the rebuild time; under it are the cache hits, the image size, the first-build time, the build context and the lint count, then the layer table with the reason for every row.

Rung 1, the naive Dockerfile. Press "1 · Stackyard naive" with "app code (app/scoring.py)" selected. Read the headline: 52.1 s to rebuild, 1 of 4 build steps from cache, a 1224.42 MB image, a 604.32 MB build context of 16 files, nine lint findings. Read the red line too: .env is inside the image. Scroll the layer table and find the row whose "Why" says it includes the changed file.

★ Step 1 · rung 1, as the lab prints it52.1 s to rebuild after app code (app/scoring.py) 1 of 4 build steps from cache · 1224.42 MB final image (419.02 MB base) 68.6 s first build · 604.32 MB build context, 16 files · 9 lint findings .env is copied into the final image

Rung 2, add a .dockerignore. Press "2 · + .dockerignore". The Dockerfile is identical; only the ignore file changed. The context falls from 604.32 MB to 4.31 MB, because .git, .venv, data/ and notebooks/ no longer travel, and the image falls to 624.41 MB. The rebuild only falls to 40.1 s. Now pick "a data file" as the change and rebuild: 0 s, 4 of 4 from cache, because an ignored file cannot invalidate anything.

★ Step 2 · the ignore file the preset uses# keep the build context to what the image needs .git .venv .env data/ notebooks/ tests/ **/__pycache__ *.pyc Dockerfile .dockerignore

Rung 3, dependency layer first. Press "3 · dependency layer first" with the app code change. The rebuild falls to 0.5 s, 4 of 5 from cache, because COPY requirements.txt . and the pip install sit above the line that copies the code. Now change requirements.txt instead: 33.4 s, 2 of 5. That is the trade you are making on purpose: you pay the install when the dependencies change, and only then.

★ Step 3 · the reorder, and nothing elseFROM python:latest WORKDIR /app RUN apt-get update && apt-get install -y curl COPY requirements.txt . RUN pip install -r requirements.txt COPY . . ENV DB_PASSWORD=stackyard-dev-123 EXPOSE 8000 CMD uvicorn app.main:app --host 0.0.0.0 --port 8000

Rung 4, a pinned slim base. Press "4 · pinned slim base". One word changed on the first line, python:latest to python:3.12-slim, and the image falls from 624.42 MB to 248.67 MB: the base itself is 43.27 MB against 419.02 MB at the time of writing. It also stops floating to whatever Python latest means this week. The lint drops DL3007 and has six findings left.

Rung 5, multi-stage. Press "5 · multi-stage". The packages install in a builder stage and only the installed result is copied into the final stage, so the pip cache and the apt layer never reach the image: 127.92 MB. Try "README.md" as the change: 0 s, because the final stage now copies only app/.

★ Step 5 · two stages, one imageFROM python:3.12-slim AS builder WORKDIR /build COPY requirements.txt . RUN pip install --prefix=/install -r requirements.txt FROM python:3.12-slim WORKDIR /app COPY --from=builder /install /usr/local COPY app/ ./app/ ENV DB_PASSWORD=stackyard-dev-123 EXPOSE 8000 CMD uvicorn app.main:app --host 0.0.0.0 --port 8000

Rung 6, non-root and lint clean. Press "6 · non-root + lint clean". --no-cache-dir on pip, a useradd and USER stackyard, the password removed from the image entirely (Compose supplies it at run time in session 5), and the CMD in exec form. Zero lint findings, 127.93 MB, 0.5 s. This is piece four of Stackyard's container kit: save it as the API's Dockerfile.

★ Step 6 · Stackyard's API Dockerfile, rung 6FROM python:3.12-slim AS builder WORKDIR /build COPY requirements.txt . RUN pip install --no-cache-dir --prefix=/install -r requirements.txt FROM python:3.12-slim WORKDIR /app RUN useradd --create-home --uid 10001 stackyard COPY --from=builder /install /usr/local COPY app/ ./app/ USER stackyard EXPOSE 8000 CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Now paste your own. Paste your session 3 Dockerfile into the edit box and press Rebuild. The lab only knows Stackyard's files and packages, so read its numbers as "Stackyard built with your Dockerfile"; the cache walk and the lint are about your file exactly.

Read the "Why" column, not only the headline. Every row says why it was cached or rebuilt: "includes the changed file", "pip cache kept in the layer", "apt lists left in the layer", "stage not needed by the final stage". Those phrases are the review comments you will be writing on other people's Dockerfiles.

Part 2 · covers which change costs what

Which file changed decides which rung pays off

5 min live

A rebuild time is meaningless without the change that caused it. The same Dockerfile is instant for one edit and slow for another, and each rung of the ladder helps a different kind of edit. The grid is every rung against the four file changes, read straight off the lab.

LiveRead the grid by column, not by row3 min▶

App code. The edit you make fifty times a day. Rung 3 takes it from 40.1 s to 0.5 s and nothing after rung 3 moves it again. This is the column people feel.

Requirements. Slow on every rung, and it should be: the packages really changed, so they really have to install. Rungs 5 and 6 are slightly slower (35.3 s against 33.4 s) because the builder's result is copied into a second stage; the lab's honest price for a smaller image.

Data file. Costs 53.2 s on the naive rung, where the 118 MB parquet file is sent and copied, and 0 s on every rung after it, where .dockerignore keeps it out of the context. Data does not belong in an image; in session 5 it arrives as a volume.

README. Still costs 0.5 s on rungs 3 and 4, because COPY . . copies it. On rungs 5 and 6, which copy only app/, it costs nothing. Copying only what the image needs is a cache decision as much as a size decision.

Self-studyA cache mount, when requirements change often2 min▶

If the requirements column is the one that hurts, Docker documents a cache mount for exactly this: RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt. The pip cache survives between builds without ever becoming part of a layer, so a changed requirements file reinstalls from local wheels instead of downloading them again. Edit rung 6 in the lab to use it and change the requirements: the modelled download time drops out of the rebuild, and DL3042 stays quiet because the cache never reaches the image.

Real world

Why .dockerignore is a speed tool too. Docker's build context documentation describes the ignore file as a way to avoid "sending unwanted files and directories to the builder", and notes the matching follows Go's filepath.Match rules, so *.md excludes markdown files at the root while "markdown files under subdirectories are still included". The lab's unit tests encode that rule: *.pyc alone leaves app/__pycache__ in the context, and the preset needs **/__pycache__ to drop it.

Part 3 · covers the anti-levers

Break it on purpose: COPY . . first, and :latest

6 min live

Two mistakes undo the ladder, and both look harmless in review. The lab has a button for each. Load rung 6, press "Break it: COPY . . first", then reload rung 6 and press "Break it: float to :latest". The lab must be able to report a worse number, or it is not measuring anything.

LiveWhy each one gets through review4 min▶

COPY . . first. It usually arrives as a fix: the pip install needs a local package, a setup.py or a constraints file, and the quickest way to make it visible is to copy everything earlier. The build still succeeds and the image is the same size (on rung 6 the extra copy lands in the builder stage, which never reaches the image). Only the rebuild changes, from 0.5 s to 35.6 s, and nobody times rebuilds in review. The lint catches it: DKR-ORDER, a lab rule, fires on the line. The real fix is to copy the one extra file the install needs, next to requirements.txt.

Float to :latest. It arrives as tidiness: "always get the newest Python". The image grows from 127.93 MB to 503.68 MB because latest is the full Debian-based image, not slim; the Python inside becomes 3.15 at the time of writing; and the build now depends on when you happen to pull. Press "base tag moved upstream" on the change list: 46.2 s, 0 of 7 cached, because every layer sits on a base that changed underneath it. DL3007 fires.

Self-studyPinning harder than a tag: digests2 min▶

python:3.12-slim is a far better pin than latest, but it is still a tag, and tags are mutable: it moves on every Python patch release and Debian update, which is usually what you want for security fixes. To freeze the base completely, Docker's best-practice guide says to pin to a digest, as in FROM python:3.12-slim@sha256:.... The lab treats a digest-pinned FROM as immune to a moved tag: add a digest to rung 6 and choose "base tag moved upstream" to see the rebuild fall to 0 s. The cost is that security updates now arrive only when you change the digest yourself; session 6 puts that decision on the release checklist.

Real world

The lint rules are real rules. hadolint, the widely used Dockerfile linter, documents DL3007 as "Using latest is prone to errors if the image will ever update. Pin the version explicitly to a release tag." and DL3042 as "Avoid cache directory with pip install --no-cache-dir". The lab implements ten hadolint rules by id, modelled on their documented intent rather than hadolint's own code, plus three rules of its own (DKR-ORDER, DKR-USER, DKR-CONTEXT) that say so wherever they appear.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · In the naive Dockerfile, a one-line change to app/scoring.py makes the pip install run again. Which cache rule causes that?

RUN is never invalidated by itself between builds; it reruns only when something above it was. Move the line that copies the changing file below the install and the install comes from the cache.

2 · On rung 2, changing the 118 MB data file costs 0 s, while on rung 1 it costs 53.2 s. Why?

An ignored file never reaches the builder. Rung 2 changes only the ignore file; the base is still python:latest. Rung 4 is the one that changes the base.

3 · A reviewer changes rung 6's base from python:3.12-slim to python:latest "to stay current". What does the lab show, and what is the better way to stay current?

latest is the full image, not slim, and it moves whenever the publisher re-points it. A pinned tag still receives patch updates; a digest receives none until you change it. Either way the change is visible in review.
