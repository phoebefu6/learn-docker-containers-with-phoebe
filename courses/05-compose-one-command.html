Part 0

Where we start

Session 1's inventory left four lines pointing at "s5": the password in a shell profile, the data file under a home folder, Postgres on localhost:5432, and a job that runs at 02:00 in the laptop's time zone. None of those belongs inside an image. They belong in the description of how the images run: which containers exist, how they find each other, which ports the laptop can see, where the bytes that must survive are kept, and where the secret is read from. That description is Compose, and for the Constructed Stackyard example it is one file, compose.yaml, piece five of the container kit.

Part 1 · covers services, the default network and ports

Inside the stack, a service name is a hostname

5 min live

Each entry under services: in a Compose file becomes one or more containers. Compose, in Docker's own words, "sets up a single default network for the app", joins every service to it, and lets each container reach the others by service name. That replaces the localhost:5432 line from session 1's inventory with something that works on every machine. The figure is the Constructed Stackyard example's stack: which name resolves to which container, and which ports cross out to Ana's laptop.

LiveService names are hostnames3 min▶

One network, created for you. When you run docker compose up, Compose creates one network for the project and attaches every service to it. You never wrote a network key, and you do not need one for a stack like Stackyard's. Inside that network, the service name is the address: the API connects to db, port 5432, and the network resolves db to whichever container is currently running the db service.

Two numbers per port, two audiences. A ports entry is "HOST:CONTAINER". The right-hand number is the port the process listens on inside its container; the left-hand number is the port your laptop opens and forwards. Docker's networking page puts it plainly: "The HOST_PORT and CONTAINER_PORT serve different purposes." Containers talking to each other use the container port and the service name, and never touch the host port at all.

Why Stackyard's db says "5433:5432". Ana still has the Homebrew Postgres from session 1 listening on 5432 on her laptop. If the db service also asked for host port 5432, the two would collide. So the container keeps its normal 5432 on the inside, and the laptop reaches it on 5433. The API never notices: it talks to db:5432 inside the network. Quote every port mapping as a string, the way the Compose reference writes them; YAML is free to read some unquoted colon-separated numbers as something other than text.

Self-studylocalhost inside a container is the container3 min▶

The most common first Compose bug on a data team is a connection string copied from a laptop: postgresql://postgres@localhost:5432/postgres. On the laptop, localhost was the laptop, and Postgres was on it. Inside the api container, localhost is the api container itself, and there is no Postgres in it. The connection is refused, and the error message rarely says "wrong host".

The rule that follows: inside the stack, address other services by service name and container port (db:5432); from your laptop, for a SQL client or a notebook you run outside Docker, use localhost and the published host port (localhost:5433). Keep the host part of the connection string in configuration, never in code, so the same code runs in both places. If you have Docker, docker compose exec api env prints the variables the api actually received; read the DATABASE_URL line and check the host is db. Your output will differ.

Real world

Docker's own example is a web app and a database. The Compose networking page walks through a two-service app, web and db, where the web container connects to the database at postgres://db:5432, while a client on the host reaches the very same database through the published host port instead. It is the same split Stackyard needs: one address for containers, one for the laptop, and Compose sets up "a single default network for the app" so the first one works without a line of network configuration.

Part 2 · covers depends_on and healthchecks

Started is not the same as ready

5 min live

The API needs the database before its first query. Compose's depends_on looks like the answer, and in its short form it is half of one: it controls the order containers are created in, not whether the thing inside is ready to answer. Postgres takes a while to initialise after its container starts, especially on a first run with an empty volume. The figure shows both versions of the Constructed Stackyard example's startup, as order only: the positions t0 to t4 are not seconds, because nothing here was timed.

LiveStarted is not ready3 min▶

The short form orders, it does not wait. depends_on: [db] tells Compose to create and start db before api. The Compose services reference is explicit that this is all it does: "Compose does not wait for dependency services to be "healthy"". A Postgres container that has started is a process that is still preparing its data directory; for a while, it refuses connections. An API that queries at startup, or a notebook cell run straight away, hits that window.

The long form waits for a condition. Write depends_on as a map and give each dependency a condition. There are three: service_started (the short form's behaviour, spelled out), service_healthy (wait until the dependency's healthcheck passes) and service_completed_successfully (wait until the dependency has run and exited cleanly).

A healthcheck is a command that answers "ready?". A healthcheck has a test (the command), an interval (how often to run it), a timeout (how long one run may take), retries (how many consecutive failures mark it unhealthy) and a start_period (a grace period while the service boots). For Postgres the command already exists: pg_isready, which the PostgreSQL 16 documentation describes as "a utility for checking the connection status of a PostgreSQL database server", where "The exit status specifies the result of the connection check." It ships inside the postgres image, so the healthcheck is one line: test: ["CMD-SHELL", "pg_isready -U postgres"]. Exit status 0 means accepting connections, and that is what service_healthy waits for.

Self-studyservice_completed_successfully for one-off jobs3 min▶

The third condition is for services that are meant to finish. The classic case on a data team is a migration step: create the tables, load the reference rows, exit. Give it its own service, say migrate, built from the API image with a different command, and make the API depend on it with condition: service_completed_successfully. The API then starts only after the migration has run and exited with status 0; if the migration fails, the API does not start against a half-built schema.

★ A migrate step the API waits for (constructed) migrate: build: . command: ["python", "-m", "app.migrate"] env_file: .env environment: DATABASE_URL: postgresql://postgres@db:5432/postgres depends_on: db: condition: service_healthy api: # ...as in the build-along, plus: depends_on: db: condition: service_healthy migrate: condition: service_completed_successfully

Chains like this read top to bottom as a contract: database healthy, then schema in place, then API. app/migrate.py is constructed for the example; Stackyard's kit does not need one yet. If you have Docker, docker compose ps shows each service's state, including health, while the stack comes up; your output will differ.

Real world

The reference says it in one line. Docker's Compose file reference, in the services section on depends_on, notes that with the short syntax "Compose does not wait for dependency services to be "healthy"" and points to the long syntax for that. The same reference lists the three conditions and the five healthcheck fields used above. Nothing about Postgres is special here: any dependency that needs time between "process started" and "ready to answer" wants a healthcheck and service_healthy.

Part 3 · covers volumes and env files

Where the bytes live when the container goes away

5 min live

Session 2 showed that a container is its image's read-only layers plus one writable layer, and that the writable layer belongs to that container. Remove the container and the writable layer goes with it. For the API that is fine: it writes nothing worth keeping. For Postgres it is everything. The figure shows the four places bytes can live in the Constructed Stackyard example's stack, and which of them survive a re-create.

LiveThree places data can live3 min▶

The writable layer: scratch space. Anything a container writes outside a mount lands in its writable layer. Remove the container and it is gone. Re-creating a container, which Compose does whenever its configuration or image changes, counts as removing it.

A named volume: storage Docker manages. Declare pgdata under the top-level volumes: key and mount it into db. Docker keeps it outside any container's lifecycle, so the database survives docker compose down and up. The mount point matters. The postgres image documentation says that for PostgreSQL 17 and below the volume goes at /var/lib/postgresql/data, not one folder higher at /var/lib/postgresql; mount it in the wrong place and the image creates an anonymous volume of its own, and the data does not persist when the container is re-created. Stackyard runs postgres:16, so the path is /var/lib/postgresql/data. From version 18 the path became version specific, so read the README again before you change the tag.

A bind mount: a host folder, shown inside. ./data:/data:ro makes the repository's data/ folder appear at /data inside the container, read-only. That is where session 1's fix pays off: scoring.py reads its path from STACKYARD_DATA, so Compose sets STACKYARD_DATA=/data and the 118 MB parquet file never goes near an image, which is exactly why the session 3 .dockerignore keeps data/ out of the build context.

And the env file: configuration, read at start. env_file: .env tells Compose to read variables from .env and hand them to the container when it starts. They are in the running container's environment, never in an image layer. .env stays out of Git (it is in .gitignore) and out of the build context (it is in .dockerignore). Remember why: in the session 4 lab, the naive Dockerfile's COPY . . put .env inside the image, where anyone who can pull the image can read it.

Self-studyenv_file vs environment precedence, and secrets as files4 min▶

Precedence. A service can have both env_file and environment. The Compose reference says values from env_file are overridden by environment. A practical split: .env holds values that differ per person or per machine and must not be committed (the password); environment in compose.yaml holds values that are the same for everyone and belong in review (STACKYARD_DATA: /data, the database host db, TZ: UTC). If the same name appears in both, the compose.yaml value wins, which is usually what you want for anything structural.

The only variable Postgres requires. The postgres image README is short on this: "The only variable required is POSTGRES_PASSWORD". POSTGRES_USER is optional and defaults to postgres. Session 1's inventory called Stackyard's secret DB_PASSWORD; in the kit it is renamed POSTGRES_PASSWORD, so one line in .env serves the database (which requires that name) and the API (whose constructed connection code reads the same name).

Secrets as files. An environment variable can show up in places you did not intend: a debug dump of the environment, a crash report, docker inspect. The postgres image offers a file-based alternative: append _FILE to the variable name, as in POSTGRES_PASSWORD_FILE=/run/secrets/postgres-passwd, and the image reads the value from that file instead, which is how it takes a Docker secret. For a laptop stack, an env file kept out of Git is the reasonable floor; for anything shared, prefer the file. Secrets for AI agents and tools are a topic of their own: Agent Secrets, session 4.

Real world

One folder too high, and the database resets. The official postgres image README warns that for PostgreSQL 17 and below the data volume must be mounted at /var/lib/postgresql/data rather than /var/lib/postgresql; otherwise an anonymous volume is created and the data does not persist when the container is re-created. It is the kind of mistake that looks fine for days: the stack runs, the tables fill, and then a routine docker compose up after an image update brings back an empty database.

Build-along

compose.yaml for Stackyard

★ 22 min · everyone builds

Constructed Stackyard example: you will write Stackyard's compose.yaml one service at a time, starting from the database because everything else depends on it. The API is built from the session 4 Dockerfile (rung 6, non-root and lint clean), already at the root of the repository. Write each step yourself in your editor or on paper first, then compare with the box. Nothing on this page was run or timed; if you later run it on your own machine with Docker, your output will differ.

The database first. Use the official image at the major version Ana already runs, read the password from the env file, keep the data in a named volume at the documented path, add the pg_isready healthcheck, and publish on host port 5433 so it does not clash with the Homebrew Postgres still on 5432. The healthcheck intervals are settings you choose, not measurements; tune them on your own machine.

The notebook, with its own small Dockerfile. The notebook needs JupyterLab on top of the same packages as the API, so it gets its own image: notebook/Dockerfile, using the repository root as its build context so it can copy the pinned requirements.txt. jupyterlab 4.6.6 is the current PyPI release at the time of writing. The nightly job, honestly. The job uses the API image with a different command. The session 4 image copies only app/, so the job's script is mounted read-only from jobs/. TZ: UTC is set explicitly, so "nightly" no longer means "whatever zone the laptop is in". A profiles entry keeps it out of a plain docker compose up; you run it once, on demand, with docker compose run --rm job. And the honest part: Compose has no scheduler. Nothing in a Compose file says "at 02:00". The trigger moves to a scheduler outside Compose, such as cron on a shared server or a scheduled CI pipeline, and away from Ana's laptop for good.

★ Step 4 · the job service, and who triggers it job: build: . profiles: ["jobs"] # not started by a plain "up" command: ["python", "jobs/nightly_scores.py"] env_file: .env environment: STACKYARD_DATA: /data DATABASE_URL: postgresql://postgres@db:5432/postgres TZ: UTC # the job's clock, written down volumes: - ./data:/data:ro - ./jobs:/app/jobs:ro depends_on: db: condition: service_healthy # the trigger lives outside Compose, e.g. a shared server's crontab # (that server's own time zone is written down in the README): # 0 2 * * * cd /srv/stackyard && docker compose run --rm job

The env file: commit the names, never the values. Commit .env.example with every variable name and a placeholder. Add .env to .gitignore. The session 3 .dockerignore already lists .env, so it cannot reach an image through the build context either.

Homework

Before session 6

30 min
  1. Draw your own stack. Take a project of yours with more than one moving part (a notebook and a database counts). Draw it the way the Part 1 figure draws Stackyard's: services in one box, the name each one uses to reach the others, and the ports the laptop needs. Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · Stackyard's api container is configured with DATABASE_URL=postgresql://postgres@localhost:5432/postgres and its first query is refused. Why?

Compose puts every service on one default network where the service name is the hostname. localhost always means "this container". The host port 5433 is for Ana's laptop, outside the network; containers use the service name and the container port.

2 · The api has depends_on: [db] in short syntax. What does that not guarantee?

Short syntax gives you start order only. To wait for readiness, give db a healthcheck (pg_isready) and write depends_on in long syntax with condition: service_healthy.

3 · Where must Stackyard's named volume be mounted in the postgres:16 container, and why?

The postgres image README names the path for PostgreSQL 17 and below and warns what happens otherwise. From 18 the path is version specific, so the README is the thing to re-read whenever the tag changes.
