Where we start

Five sessions in, the Constructed Stackyard example has an inventory, a Dockerfile read line by line, an API image measured on the bench and a compose.yaml that stands up the notebook, the API and Postgres. Part 1 · covers multi-stage builds

Build in one stage, ship from another

5 min live

A Dockerfile can have more than one FROM. Each FROM starts a new stage, you name a stage with AS <NAME>, and COPY --from copies files out of one stage into another. Docker's documentation puts the point in one phrase: you copy artifacts across, "leaving behind everything you don't want in the final image". The figure is rung 5 of the session 4 lab, built on the Constructed Stackyard example: what the builder stage holds, and the one copy that crosses into the image you ship.

LiveWhat stays behind in the builder3 min▶

Rung 4, one stage. In the session 4 lab, the pinned slim Dockerfile prints a 248.67 MB image. Two layers carry weight it does not need at run time: the apt-get install curl layer at 40.3 MB, with the apt lists left inside it, and the pip install layer at 160.78 MB, which is 80.39 MB of installed packages plus 80.39 MB of pip's download cache. Both are frozen into the image, because a layer keeps every byte it wrote.

Rung 5, two stages. The install moves into a stage named builder, with --prefix=/install so the installed packages land in one folder. The final stage starts again from python:3.12-slim and copies just that folder with COPY --from=builder /install /usr/local, then copies only app/. The lab prints the final stage as base 43.27 MB, plus 80.39 MB of packages, plus 4.26 MB of app code: 127.92 MB. The pip cache, the requirements file and the builder's working folder are still in the builder, which nobody ships.

What the builder costs you. Nothing at run time, a little at build time: BuildKit builds the builder stage as part of the build, and the cache rules from session 4 still hold inside each stage. Docker's documentation adds one useful detail: "BuildKit only builds the stages that the target stage depends on." A stage nothing copies from is skipped. Rung 6 then adds --no-cache-dir, which shrinks the builder's pip layer to 80.39 MB as well; the shipped image barely moves (127.93 MB, one small useradd layer more), because the cache never reached it anyway.

Self-studyMulti-stage when you need compilers3 min▶

The python image's documentation describes the slim variant as "only the minimal Debian packages needed to run python": the toolchain for compiling extension modules is not there. Stackyard never needs it, because at the time of writing every one of its fourteen packages ships a ready-built wheel for Python 3.12 (a manylinux wheel, or a pure-Python one). Add a package with no wheel for your platform and pip install on slim fails trying to compile.

Multi-stage turns that into a clean trade. Install the compilers in the builder, build there, and copy only the result. The final stage never sees the compilers, so they cost the shipped image nothing. A sketch of the shape, if you have Docker:

★ The shape: compilers in the builder only (sketch)FROM python:3.12-slim AS builder RUN apt-get update && apt-get install -y --no-install-recommends build-essential \ && rm -rf /var/lib/apt/lists/* WORKDIR /build COPY requirements.txt . RUN pip install --no-cache-dir --prefix=/install -r requirements.txt FROM python:3.12-slim COPY --from=builder /install /usr/local # no build-essential here: the final stage never installed it

One caution: anything compiled in the builder that links to a system library at run time still needs that library in the final stage. If the final image fails on import with a missing .so file, install the run-time library (not the compiler) in the final stage.

Real world

The documentation's own definition of the win. Docker's "Multi-stage builds" page describes the pattern as copying artifacts from one stage to another, "leaving behind everything you don't want in the final image". In the session 4 lab that sentence is the difference between 248.67 MB and 127.92 MB for the same fourteen packages and the same four app files, with no change to a single line of Python.

Part 2 · covers slim, alpine and distroless

Which base: slim, alpine or distroless

6 min live

The base image is the biggest single choice in the Dockerfile, and for Python it is a genuine argument among experienced people, not a solved question. Below are the three common answers, what each one contains, and what the evidence says, with its dates. The Constructed Stackyard example sits in the bottom row of the figure, because the answer depends on your packages, not on the base alone.

LiveCheck your own wheels before you choose3 min▶

The fact underneath the argument. The official alpine variant uses musl as its C library, not glibc, and the python image's documentation warns that "software will often run into issues depending on the depth of their libc requirements/assumptions". For Python the practical question is wheels. A manylinux wheel is built against glibc and cannot be used on musl. PEP 656, now Final, defines the musllinux platform tag so projects can publish wheels built for musl-based distributions such as Alpine. If every package you need publishes a musllinux wheel for your Python and your processor, pip installs ready-built files on alpine. If one does not, pip compiles it from source, and you need a compiler in the image to do it.

Stackyard, checked on PyPI at the time of writing. numpy, pandas, scipy, pydantic-core and psycopg2-binary all publish musllinux wheels for CPython 3.12 on x86_64. scikit-learn 1.9.1 publishes manylinux, macOS and Windows wheels, and no musllinux wheel. So on alpine, pip builds scikit-learn from source. The session 4 lab models exactly that on its alpine side road: apk add build-base to get a compiler (modelled at 196 MB), and a modelled 420 s to compile. It prints a first build of 459.5 s, a rebuild after a requirements change of 454.9 s, and a 302.62 MB image, against rung 6 on slim at 36.9 s, 35.3 s and 127.93 MB. The 18.05 MB base did not survive contact with one missing wheel.

The one-minute check, for your own project. For each package in your requirements file, look at the release's file list and search for a filename containing both your Python tag (cp312) and musllinux. On the PyPI website that is the "Download files" list. Or, with Python on any machine (your output will differ, and an empty list means no musllinux wheel for that version):

★ Does this release ship a musllinux wheel for Python 3.12?python3 -c "import json, urllib.request as u; d = json.load(u.urlopen('https://pypi.org/pypi/scikit-learn/1.9.1/json')); print([f['filename'] for f in d['urls'] if 'musllinux' in f['filename'] and 'cp312' in f['filename']])"

Run it for every pinned package, not only the famous ones. The answer is a property of your exact list on the day you check, which is why the same team can reasonably choose alpine one year and slim the next.

Self-studyThe case for and against alpine, by date4 min▶

Against, 2020 (reported). Itamar Turner-Trauring's article "Using Alpine can make Python Docker builds 50x slower" on pythonspeed.com, first published 2020-01-29, reports his own test: a build that took about 1,557 s on Alpine against about 30 s on Debian slim, and an Alpine image that came out larger, 851 MB against 363 MB. The cause was the one above: packages with no musl wheel at the time, compiled from source, with the compilers left in the image.

The standard that changed the picture. PEP 656 defined the musllinux wheel tag, and it is now Final. Projects started publishing musl wheels alongside their manylinux ones. At the time of writing, most of Stackyard's heavy packages do.

Softer, 2026 (reported). The same author updated the article on 2026-01-30. He writes that musllinux wheels make Alpine "much less of a problem these days", and in the same update says he remains "personally wary of using musl". Both statements come from the same person, a few lines apart, and both are fair: the wheel gap has mostly closed, and musl still behaves differently from glibc in places your tests may not reach.

For distroless. The distroless images contain "only your application and its runtime dependencies", with no package manager and no shell. The static base, static-debian13, is "around 2 MiB" by the project's own account, and a python3-debian13 image is published. The trade-off is operational: no shell means nothing to docker exec into when something goes wrong at 2 a.m., and no pip means every package arrives through a COPY --from out of a builder stage. The :debug tags add a busybox shell for exactly that moment. No size is quoted here for the Python image: it was not measured.

Where that leaves you. Not with a winner. Slim is the default the session 4 lab measured and every Stackyard package installs on it from wheels. Alpine is smaller as a base and can be a fine choice when your exact package list has musllinux wheels and your tests run on it. Distroless removes the most and asks the most of your debugging habits. Check your packages, write the reason in the Dockerfile as a comment, and revisit it when the list changes.

Real world

One author, two dates, both honest. In 2020, Itamar Turner-Trauring reported an Alpine build of about 1,557 s against about 30 s on Debian slim, with the Alpine image larger at 851 MB against 363 MB (reported, his own test). In his 2026 update to the same pythonspeed article, he writes that musllinux wheels make Alpine "much less of a problem these days", while staying "personally wary of using musl". The evidence moved; the caution did not disappear. Your packages decide which of his two sentences applies to you.

Part 3 · covers secrets in layers and scanning

Secrets never reach a layer

4 min live

An image is a stack of layers, and session 2 showed that each layer records a set of filesystem changes: additions, deletions, modifications. A deletion is a change recorded on top; it does not reach back and erase the bytes underneath. That one fact decides how secrets have to be handled. The figure is the Constructed Stackyard example's naive Dockerfile with a tempting fix added, beside the mechanism that actually keeps a secret out.

LiveThree ways a secret gets into an image3 min▶

1 · Copied in with the project. The naive rung in the session 4 lab copies the whole folder with COPY . . and no .dockerignore, and the lab prints the consequence in red: ".env is copied into the final image". Adding RUN rm .env later does not help. The file disappears from the container's view, but layer 3 still holds its bytes, and anyone who can pull the image can unpack that layer. The fix is to keep it out of the build context in the first place: .env in .dockerignore, which the standard .dockerignore from session 3 already does.

2 · Written into ENV or ARG. Rungs 1 to 5 of the lab carry ENV DB_PASSWORD=stackyard-dev-123, and the lab's lint flags it as DL3064, modelled on hadolint's rule: "Potentially sensitive data should not be used in the ARG or ENV commands". An ENV value is not in a file layer; it is in the image configuration, which is just as readable, and every container started from the image inherits it. Docker's "Build secrets" page is direct: "Build arguments and environment variables are inappropriate for passing secrets to your build" because "they persist in the final image". Rung 6 removes the line entirely.

3 · Needed during a build step. Sometimes a build genuinely needs a secret, for example a token for a private package index. The right tool is a build secret: docker build --secret id=...,src=... passes it in, and RUN --mount=type=secret,id=... exposes it to that one RUN only. It is never written to the layer the RUN produces. Stackyard's API does not need one: its packages come from public PyPI.

And at run time. The password the running API and database need arrives when the container starts, never when the image is built: from .env through Compose's env_file, as session 5 set up (where DB_PASSWORD became POSTGRES_PASSWORD), or from a file, as the postgres image allows with POSTGRES_PASSWORD_FILE. Secrets used by AI agents and tools are their own subject, taught in Agent Secrets, session 4.

Self-studyScanning, as a category3 min▶

An image scanner reads the packages installed in each layer (the operating system's packages, and often the language packages too) and compares their names and versions with lists of known vulnerabilities. It reports what it finds by package and version. Several free and commercial tools do this, some built into registries and CI platforms; which one your organisation uses is a decision for whoever owns your pipeline, and the category matters more than the brand.

Two consequences for a data team. First, a smaller image gives a scanner less to report on: every package you leave in the builder is a package nobody has to triage. The distroless project makes the same argument for its images, that a smaller runtime "improves the signal to noise of scanners (e.g. CVE)". Second, a scanner reports packages, not intent: it cannot tell you that a .env file sits in layer 3, so it does not replace the checklist row that says no secret in any layer.

Pinning interacts with scanning too. A digest-pinned base never changes until you change it, so security fixes to the base arrive only when someone updates the line. That is why the release checklist pairs the pin with a review date.

Real world

The documentation says it in one line. Docker's "Build secrets" page: "Build arguments and environment variables are inappropriate for passing secrets to your build," because "they persist in the final image". The recommended path is the secret mount, which exposes the secret to one RUN instruction and nothing else. Every ENV password in rungs 1 to 5 of the session 4 lab is the thing that sentence warns about.

Homework

After the capstone

30 min
  1. Split one of your images into two stages. Take a single-stage Dockerfile you own, move the install into a builder stage and COPY --from only what the run needs. If you have Docker, compare docker image ls before and after; your output will differ.
  2. Run the wheel check on your requirements. For every pinned package, look for a cp312 (or your Python's) musllinux wheel on PyPI. Write one line in your Dockerfile saying which base you chose and why, with the date you checked.
  3. Hunt for secrets in your Dockerfiles. Search every Dockerfile you own for ENV and ARG lines with PASSWORD, SECRET, TOKEN or KEY in the name, and check that .env is in every .dockerignore. If an image already shipped with one, rotate the secret: removing it from the next build does not remove it from the images already pulled.
  4. Run the release checklist on a real image. Copy the ten rows, run them against one image you or your team ship, and write the result beside each row. Bring the weakest row to your next team review.
Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · A Dockerfile has COPY . . as layer 3, which brings .env in, and RUN rm .env as layer 5. Is the secret out of the image?

Each layer is a set of filesystem changes, and a later deletion does not rewrite an earlier layer. Keep .env out of the build context with .dockerignore, and pass anything a build step needs with a secret mount, which is never written to a layer.

2 · In the session 4 lab, Stackyard's image goes from 248.67 MB at rung 4 to 127.92 MB at rung 5 with multi-stage. What did the multi-stage build leave behind in the builder?

The builder's pip layer is 160.78 MB: 80.39 MB of installed packages and 80.39 MB of cache. COPY --from=builder /install /usr/local takes only the packages. The rung 4 apt layer does not appear in rung 5 at all, because no apt install is needed.

3 · A colleague asks: "Should our Python data API use alpine?" What is the honest answer?

Both sides have evidence with dates. Where wheels exist, alpine installs from ready-built files; where one is missing (scikit-learn 1.9.1, for Stackyard), pip compiles it, and the session 4 lab's alpine side road prints 302.62 MB and 459.5 s, modelled, against 127.93 MB and 36.9 s on slim. Your package list decides.
